04 / OUR ASSESSMENT

设计合理，验证能力有明确边界

以下是基于论文与静态代码阅读的评价，未作本地性能或稳定性复现。

值得借鉴的设计

  • 操作集中：模型围绕一个物体程序工作。
  • 可以主动取证：测量工具补充反馈信息。
  • 交付有门槛：验证结果绑定最新修改。
  • 运行可追溯：保存对话、工具、结果与成本。

成熟度边界

  • 外形与功能：局部检查会漏掉整体不合理。
  • 检查豁免：模型可声明允许重叠等例外。
  • 运行隔离：执行 Python 的子进程并非完整沙箱。
  • 恢复能力：历史与派生编辑不等于多对象事务回滚。

定位：工程实现较完整的任务专用研究工具。项目配置标为 Alpha；论文附录 B.5 展示检查覆盖不足的失败案例。

Articraft · SDK 操作部件与关节我们 → 明确的身份与归属操作
Articraft · probe_model 测几何我们 → 历史视图＋点云取证
Articraft · 验证当前程序版本我们 → 归属、点云、检查版本一致
05 / EXECUTION FLOW

一个任务，从启动到交付

沿着代码执行顺序，看 Articraft 怎样完成“生成一个可以向前拉开的单抽屉柜”。

依据本地代码静态阅读整理；以下工具选择、重叠与修复是教学示例，并非真实运行记录。中间行动由模型选择，不是固定流水线。

模型 · 决定做什么设计物体、写代码、选择检查与修改。
Harness · 组织执行调用模型、派发工具、回传结果、判断能否结束。
SDK / 检查器 · 实际计算构造几何、部件和关节，执行检查与测量。
01

接收任务：先准备一次运行

命令入口解析模型配置、需求与可选图片，准备任务目录和运行记录，然后创建 ArticraftAgent。

generate → _run_generate() → runner_cli.main()
→ run_from_input() → execute_single_run()
→ await agent.run(user_content)

这时还没有柜子几何，只有任务和运行环境。

cli/main.py · _run_generate · single_run.py · execute_single_run
02

初始化：给模型说明书、工具和一份工作文件

ArticraftAgent.__init__() 准备模型客户端、系统提示、SDK 文档上下文、工具注册表和检查状态；进入 run() 后确保代码文件存在并建立初始对话。

模型可用

任务要求 + SDK 文档
读文件 / 找示例 / 编辑 / 编译 / 测量

程序维护

model.py + 对话记录
代码版本、检查状态、轮数和费用

model.py 是持续修改的核心成果；不是每轮重新开始一个独立任务。

harness.py · ArticraftAgent.__init__ / run · tools/__init__.py · build_tool_registry
03

调用模型：下一步由模型决定

await llm.generate_with_tools(
system_prompt, messages=conversation, tools=工具说明
)

模型可能先找移动关节的示例，也可能直接写代码。Harness 执行请求，把工具结果追加到 conversation，再调用模型。

例如：模型请求 find_examples → 程序查找示例 → 结果进入对话 → 模型继续。

一次任务通常包含多轮 API 调用；“先查示例”并非强制步骤。

harness.py · run / _execute_tool_calls_batch
04

写第一版：把设计表达为程序

模型通过编辑工具写入 model.py，定义物体结构及 run_tests() 等内容。程序实际修改文件，并更新代码版本。

柜体部件←移动关节
方向 + 行程→抽屉部件
模型提出修改 → 编辑工具落盘 → 代码变成 v1 → 尚未验证。

编辑工具随 provider 不同，可使用 apply_patch、replace 或 write_file。

harness.py · _execute_tool · harness_compile.py · mark_code_mutated
05

编译检查：让代码接受真实执行

模型调用 compile_model 后，程序才实际加载建模代码、构造对象并检查。

model.py → 加载执行 → object_model
→ 模型编写的 run_tests()
→ 编译器基础检查 → 汇总检查报告
→ 成功：URDF 等结果 / 失败：错误反馈

基础检查包含结构有效性、单一根部件、网格资产、孤立部件、当前姿态的部件重叠等。

示例反馈：抽屉过宽，与柜体侧板重叠。错误加入对话，交给模型决定下一步。

任务测试由模型编写；基础检查也有覆盖范围，并支持显式豁免。通过检查不等于外观与全部运动姿态都正确。

compiler.py · compile_urdf_report / _run_compiler_owned_baseline_tests
06

调查与修复：需要时拿“量尺”再看一眼

模型可以直接修复，也可以调用 probe_model 提交测量代码。工具对当前几何执行计算并返回 JSON，测量本身不修复物体。

发现重叠→测量侧向间隙→修改抽屉宽度→重新编译

这个循环主要使用代码、检查报告和数值反馈；并非每轮都把渲染图交给模型观察。测哪里、是否测量，由模型决定。

probe_model/description.py · 工具约定 · probe_model/tool.py · 执行测量
07

结束检查：说“完成”还不够

模型尝试结束时，Harness 检查最后一次成功编译是否对应当前代码版本。

可以结束

写 v1 → 检查 v1 通过 → 结束

必须继续

检查 v1 通过 → 改成 v2 → 结束
↳ 提醒：请先 compile_model 检查 v2

有成功检查报告
且 最后成功编译版本 == 当前代码版本

编译通过不会立刻强制结束；模型还可以继续调查或修改。上述条件在尝试结束时把关。

harness.py · _handle_finish_attempt · harness_compile.py · latest_code_is_fresh
08

返回并保存：把运行变成可查看的记录

成功后，外层 single_run.py 整理最终代码、URDF、检查警告与运行信息，写入记录。异常或达到轮数、费用限制时，走失败处理路径。

部分代码已经写出 ≠ 任务成功；“成功”表示当前版本满足已执行的检查。
single_run.py · execute_single_run · record_persistence.py · write_success_record
Harness 在这里的职责不替模型决定抽屉多宽；让模型有工具可用、收到真实反馈，并确保交付的版本与通过检查的版本一致。

借鉴“模型选择行动 → 程序执行 → 真实反馈 → 再决定”的循环，工作对象则换成持续更新的场景状态。
