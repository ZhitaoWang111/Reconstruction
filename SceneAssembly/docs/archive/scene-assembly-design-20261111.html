场景组装：agent 判断，几何作证据

agent 决定"做什么"：放在哪、朝哪面、立在谁上面、资产能不能用。 harness 负责把 agent 的决定精确做到，并如实测量。 几何结果不会自动写进状态，只以证据，或 agent 主动调用的执行器的形式出现。

01为什么让 agent 判断

几何在连续量上很准，在几类离散判断上无能为力

48 / 52
个物体，配准最优解和次优解残差比 <1.2，多数相差 180°。正反面靠几何分不出来。
4 / 52
个物体，关键帧轮廓 IoU 在最优和次优朝向之间能拉开 ≥0.05。IoU 也分不出来。
3.2 cm
竖直锁定配准的残差中位数。给定朝向之后，几何对平移的求解很准。
问题几何看到的看图看到的
正反面toaster oven 两个朝向 IoU 0.63 vs 0.62；shelf 0.90 vs 0.89。几何最优解经常恰好是背面。一个朝向是平板背面，另一个能看到门、旋钮和书，与关键帧一致。
倒置SAM3D 有 6 个物体整体倒置。冰箱倒置前后残差 5.3 vs 5.1 cm，IoU 0.88 vs 0.90，几何检测不出来。微波炉脚朝上，冰箱出水口在下面，一眼可见。
支撑nightstand obj_0050 扫描底面在 0.23 m，stool 在 0.17 m。按扫描底面放会悬空。关键帧里它们立在地上，是扫描缺了下半截。
支撑物点级检测给出候选：tv 下方有 250 个点属于柜子 obj_0008。"电视放在柜子上"是语义判断，确认后成为一条关系。
资产本身mirror 所有朝向 IoU ≈0.10；couch 残差 20 cm；kitchen counter 是一块 5 cm 薄板；guitar case 平躺。决定缩放、接受、标记，还是重新生成。
结论
离散判断（正反、倒置、支撑、资产好坏）交给 agent；连续量的精确求解（贴面、局部配准）做成执行器，由 agent 指定意图和搜索窗口后调用。
批 1 验证
在 agent 没见过的留出帧上，按残差最小选朝向（0.436）比完全不管朝向（0.472）还差；agent 看图后达到 0.532。

02分工与架构

agent 只能通过工具读证据、提修改 · harness 是仪器加账本

输入 · 两份交接文件
assembly_handoff/v2 + 实例识别场景交接
52 个 USD 资产 · SAM3D 旋转 · 资产尺寸与可信度 · 扫描点云 · 每物体 1–3 张关键帧（RGB + mask + 相机）· 内参 · floor_z
另有 500 帧 GT（只用于评估）和 ScanNet 房间剩余网格（支撑面）
harness · 证据（只读）
物体卡 · 候选对比图 · 资产转台 · 精确相机渲染 · 测量
  • 每个物体 5 个候选位姿：SAM3D + 4 个 yaw 起点的锁竖直配准
  • 所有渲染都在关键帧的真实相机下（真实内参 + camera_to_world），和照片逐像素对齐
  • 确定性的东西在这里一次算好，不重算、也不靠模型记
agent · 判断与决定
起点 · 正反 · 倒置 · 支撑 · 缩放 · 资产问题 · 顺序
  • 每个物体的起点：选 SAM3D、选某个配准候选，或直接给绝对值
  • 正反、倒置、90° 翻转；支撑、贴墙、挂墙关系；该调用哪个执行器
  • 缩放幅度；资产接受、标记还是要求重生成
  • 处理顺序、何时重开已接受的物体；每次调用附理由，逐条回应警告
harness · 执行
直接操作 · 执行器（窗口由 agent 给）
位姿精确执行；落到支撑面、局部配准不会跳出 agent 给的窗口，所以不会把已判定的正面翻到背面
harness · 提交关口
propose → 核验渲染 + 警告（只警告，不否决）
穿插 · 悬空 · 离扫描底面太远 · 缩放过大 · 超出扫描范围
harness · 状态与日志
不可变版本链 · 关系图 · stale 传播 · 调用日志
每次 commit 写 states/vNNNN.json，旧版本不改；每轮的思考摘要、调用和看过的图全部存档
流程末端 · Isaac Sim
物理沉降 · 导出 scene.usd
漂移量交回 agent。循环内的渲染全部离线（trimesh + embree），Isaac 只在最后用。
为什么离线
循环内每个物体要看几十次图。离线渲染直接用 ScanNet 内参和 camera_to_world，逐像素对齐、能直接算 IoU；单资产全幅 0.16 s，52 个资产（214 万面）整场景全幅约 1 s，可并行、可复现，不依赖 Isaac 进程。
为什么还要 Isaac
真正起碰撞作用的是凸包 / 凸分解碰撞体，不是视觉网格。凸包会填满凹处（比如床头板和床面之间），只有物理沉降能发现"放上去会被弹开"。

03批次

一次会话处理 4–6 个物体 · 整个场景 10–13 批

三个时间尺度

层级单位规模说明
工具调用一个物体1一次看图、一次 propose
会话一批物体4–6，默认 5同一上下文里连续做多轮工具调用。设计对象是这一层
一轮整个场景10–13 批加一次整体复查和一次物理沉降

批次为什么夹在 4–6

1
关键帧天生是多物体视图
某个物体的主关键帧里，中位还能看见 6 个其他物体（最少 3、最多 16）。一次只处理一个物体，这些邻居的图就被浪费，下一批再取同一张图重新计费
2
图像不能全量共享
145 个（物体, 关键帧）对只对应 116 张不同的图；贪心覆盖全部 52 个物体至少要 45 张关键帧，一次会话塞不下
3
token 预算
整帧 1296×968 约 1670 token，768² 环绕图约 790，512² 裁剪块约 350。5 个物体 × 约 4 张图 ≈ 20–25k，加目录、约定和状态约 10k，一次会话约 35k。到 8 个物体就会出现"后一个物体的决定要重开前一个"
这个场景没有自然分区：按质心单链接聚类，1.0 m 阈值切出的簇大小是 22/13/6/3/2/2/2/1/1；按"同帧共现"做弱连通，52 个物体连成一块。所以切批必须按规则算。

切批规则（按优先级）

1
支撑依赖先行
同一支撑连通支尽量进同一批；切开时，支撑物所在的批严格在前。实测 11 条支撑边，最长链 2 层：toaster / dish rack / toaster oven → kitchen counter → cabinet obj_0042
2
共享关键帧
同批物体在主关键帧里互相可见；一批 5 个物体通常只要 3–5 张新图
3
同批不超过 6 个
支撑物 + 依赖物的一组通常自然落在 5–6 个

按规则粗切的示意批次运行时由支撑图 + 共视矩阵现场计算

05状态

沿用 InstanceRecognition 的不可变版本链 · 初始全部 unplaced

字段内容
objects[oid].pose(x, y, z, yaw_deg, up, scale_xy, scale_z)。up 是 6 个正交朝向之一（倒放、侧放）；(x, y) 是占地中心，z 是最低点高度
objects[oid].statusunplaced → placed → accepted；另有 stale（支撑物变动后）和 flagged（资产问题）
objects[oid].support支撑物：floor 或另一个物体
relationssupported_by、against（墙或物体）、attached（挂墙）
asset_flags问题描述，以及处理请求：regen / accept_scaled / drop
notesagent 写的理由
缩放拆分
原设计是"三轴缩放"。批 1 实测：资产高度都在真值 6% 以内，占地常常不对。只有统一缩放时，缩床修占地会把床面压低 16 cm，床上物体全部下沉（第 1 轮 0.342）。拆成 scale_xy / scale_z 后第 2 轮 0.532。占地仍是两轴同比例，批 1 的床说明两轴需要分开（见 11）。

07提交与核验

和 InstanceRecognition 的 propose_update / commit_update 同一套模式 · 预览是渲染图

agent 选动作

核验轮 · 强制
agent 看渲染和警告
警告类型：穿插 >2 cm · 声明的支撑面有空隙或陷入 · 无支撑却悬空 · 最低点离扫描底面 >6 cm · 缩放偏离 1 超过 20% · 占地中心超出扫描范围
不满意
修改参数或换执行器，重新 propose
设计：核验最多 2 轮，之后必须决断（提交、标记或放弃）。
实现：目前不限轮数
满意 · commit
写入 v(N+1)，旧版本不改
理由必须逐条回应警告。这是要求解释，不是否决。
支撑物移动过的话，上面的物体标 stale，等复查
批 1 教训
"只要求解释、不否决"被一个错误理由钻了空子：穿插警告被解释成"碰撞体外扩"放行了四次，结果肉眼可见穿模。原因之一是物体卡给的扫描占地是轴对齐包围盒，房间转了约 18°，床被放大了。改进方向见 11。
