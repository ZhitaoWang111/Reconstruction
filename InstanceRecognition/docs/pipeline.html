从一张 RGB 图到一个跨帧物体

GPT 判断画面里有什么，SAM3.1 按这些判断切出 mask，投影器把每个 mask 像素落成三维点， Harness 再逐窗口决定这些点属于哪个物体。三个模块，前两个产出数据，第三个消费数据。

01SAM / GPT 出 mask

src/inference/label_frames.py · gpt_sam31.py · sam31_segment.py

输入
一批原始 RGB 帧（JPEG），加一份列出帧号的 batch JSON。 不含任何 mask、深度或时间上下文。
输出
每帧一组二值 mask PNG，外加一份把 mask 与类别、置信度、来源哈希绑在一起的 predictions.json。mask 是帧内局部的，没有跨帧身份。
命令
python -m src.inference.label_frames → python -m src.inference.gpt_sam31（两步，顺序执行）

两步分工先 GPT，后 SAM

GPT 那一步只看图，说出画面里有哪些类别、每类该用什么提示词去分割。 SAM 那一步消费这些提示词，把文字落到像素上。两步分开是因为它们失败的模式不同： 类别判断错要换 prompt 重跑，分割错要换阈值或权重重跑，重跑范围不一样。

1.1 · GPT 请求的形状

{
  "model": "openai/gpt-6-sol",
  "messages": [
    {"role":"system", "content": <prompt_en.txt>},
    {"role":"user", "content":[{"type":"image_url",
       "image_url":{"url":"data:image/jpeg;base64,…", "detail":"high"}}]}
  ],
  "response_format": {"type":"json_schema", "strict":true, …}
}

// 模型必须返回这两个数组，其余字段一律不允许
{ "categories": [ … ], "unresolved_regions": [ … ] }

strict json_schema 是在解码时约束输出，不是"请返回 JSON"的口头要求。 每条 category 固定六个字符串字段：category、sam_prompt、 certainty（clear/uncertain）、visible_scope（whole/partial/unclear）、 evidence、ambiguity。

代码随后用 validate() 再验一遍，且比 schema 更严： category 与 sam_prompt 不能为空或纯空白， category 大小写折叠后不能重复。unresolved_regions 每项固定 location 与 reason 两个字段。

1.1.1 · 标签 prompt 实际约束了什么

prompt（src/inference/prompts/prompt_en.txt，13 行）不是泛泛的"描述这张图"，而是给 SAM 写提示词的规则，几条硬约束值得记住：

  • 一个类别只列一次，即使画面里有多个实例——实例数由 SAM 决定，GPT 不返回计数、框或 mask。
  • 优先整体物体而非附着部件；排除墙、地板、天花板。
  • 成对可见的鞋必须标成 pair of shoes，且不许再单列成员；只有一只时用 unpaired shoe。手套同理。
  • evidence 必须描述可见形状或外观，不能复述类别名；无歧义时 ambiguity 留空。

# 一个提示词可以返回多张 mask（两把椅子 = 两条候选）
# 全部候选保留成 PNG → 按 sam_score 取前 16 → 重编号 instance_id = 1,2,3…

instance_id 是每帧局部的，只在当前帧有意义。 跨帧身份是 03 才建立的东西，两者不能混用。

预算筛选只决定"哪些入选"，不决定编号顺序。 实现在 sam31_segment.select_within_budget：先按 sam_score 降序取前 max_masks，再按原始候选顺序重新排一遍才赋 instance_id。 所以 instance_id 小不代表分数高——实测 frame 11 的 8 个实例里， id 5（shoe, 0.801）排在 id 4（curtain, 0.770）之前，就是原始顺序，不是分数序。 落选者记在 excluded_by_budget，其二值 mask 仍然写盘，只是不进 instances。

另一处容易误读：max_num_objects 与 multiplex_count 在 load_predictor 里被写死为 16（DEFAULT_MAX_MASKS）， 与命令行 --max-masks 无关。--max-masks 只控制入选并写入 instances 的数量，上限 32（uint32 位图容量），不改变模型侧容量。

02mask 投影到 3D

src/geometry/assemble_perception_source.py · amb3r_mask_source.py

输入
01 产出的 perception/ 目录，加 AMB3R 的逐帧点图与位姿（vo_uniform500）。
输出
一份可被 Harness 直接消费的 source 目录：每帧一份 npz（世界坐标点 + 归属位图）， 一份 manifest.json，加页面用的 JS asset。
命令
python -m src.geometry.assemble_perception_source → python -m src.geometry.amb3r_mask_source

原理

AMB3R 对每一帧预测一张逐像素深度图：图上每个像素都对应一个三维点， 世界坐标由「该像素的深度 + 该帧的相机位姿」直接算出来。投影要做的只有一件事—— 把 mask 覆盖到的那些像素挑出来，取出它们已经算好的三维点。

所以这一步没有射线投射，也不需要判断「这条视线先撞到哪个表面」： 深度是逐像素给定的，一个像素最多对应一个点，遮挡关系在 AMB3R 里已经解过了。 投影器只负责对齐网格、筛选像素、把点搬到世界坐标系。

三张图是同一个 mask、同一帧。2D 图给出像素范围，相机视角图证明这些像素落回原位， 侧方视角图给出它们的空间形状——如果深度错了，椅子会被拉成一片贴在墙上的平面。

两步分工先装配，后投影

装配器不投影任何点。它只把 01 的两半（labels 与 masks）对齐成一份可投影的清单， 并证明它们确实属于同一次推理。投影器再读这份清单，把像素落成三维点。 分开是因为校验很便宜（秒级），投影很贵（全量重算），失败的判定应该在便宜的那一步做。

装配器校验四道，任何一道不过就整批停住：

  • 帧对齐——labels 与 masks 的 sequence_index 与 source_frame_id 必须同时相等。两半按不同的键索引（labels 按采样序号，masks 按源帧号），这是最容易错配的地方。
  • 标签一致——mask 记录的 provenance.labels_sha256，必须等于当前 label 文件重算的 SHA-256；不等说明 mask 是另一批 label 生成的。
  • 图像一致——batch、labels、predictions 三方记录的 RGB 哈希，都要等于从 --frames-dir 重新算出的图哈希。
  • 模型唯一——所有帧的 gpt_model 必须只有一个值。

另外两条硬约束：实例数必须等于 instance_count，且每帧不超过 32（uint32 位图容量）；采样序号必须是从 0 起的连续整数，否则观测 ID 会错位。

装配器不复制 mask：写进 manifest 的是相对输出目录的路径，原地引用 perception/ 里的文件。所以 source 目录和感知产物必须一起保留。

装配产物故意没有 lifting_policy。 Harness 只接受它认识的那个 policy；缺这个字段，Harness 直接拒绝。 如果装配完就能被 Harness 吃下，说明有人跳过了投影，模型看到的将是没有三维证据的观测。

投影时做的四件事

  1. 对齐网格。原始 RGB 与 mask 是 1296×968，AMB3R 输出 392×518。中间两步： 先缩放到 640×480，再按 518:392 的比例中心裁剪成 634×480，左边裁掉 3 像素（(640 − 634) // 2），最后缩到 518×392。 这三步用最近邻，保住二值归属；mask、RGB 采样、页面底图必须走完全相同的变换， 否则每帧偏几像素。
  2. 筛像素。只保留「属于某个 mask」且「AMB3R 置信度 ≥ 0.3」的像素。 这批数据上丢弃不是接近 0——实测帧 0 丢 1.42%（1776/125496 网格像素）， 帧 75 丢 4.93%（5496/111373），帧 149 只丢 0.02%。帧间差异很大， 低置信区集中在低纹理或远距离处。
  3. 搬到世界坐标。用评测文件里的 sim3_oracle_scale 把点从 AMB3R 坐标 变换到与 GT 对齐的世界坐标（P_world = s·R·P_amb3r + t，当前 s = 0.8875）。同一个变换也把背景点云带到同一个坐标系，两者才能叠在一起看。
  4. 记归属。每个像素可能同时属于多个 mask，所以用一个 32 位整数记「属于哪几个」， 而不是记单个编号。

每帧写出一份 npz，六个键：

键形状说明
points_world(K, 3) float32世界坐标
rgb(K, 3) uint8原图采样色
mask_bits(K,) uint32第 i 位表示属于第 i 个 mask
pixel_indices(K,) int64该点在 518×392 网格里的扁平序号
grid_shape_hw(2,)(392, 518) —— 注意是 h, w
sequence_index标量采样序号
mask_bits 用位而不是编号，是为了保住重叠。 两个 mask 在同一像素重叠时，这个点会有两位同时为 1。 换成"每点记一个 instance_id"就必然丢弃其中一方。viewer 用洋红色显示这些重叠点。
这份几何是"对着 GT 拟合"的，不能当作 AMB3R 的独立精度。 sim3_oracle_scale 使用 GT 相机位姿求解，所以同一份评测文件里两个口径差很多： 自尺度 se3_native_scale 的 ATE 为 0.257 m、五厘米 F-score 为 0.099； 对 GT 拟合后 ATE 降到 0.091 m、F-score 升到 0.562。 提升里有一大半是 GT 的功劳。投影链路只把这份几何当作"够用的逐像素深度"， 任何页面文案都不得暗示独立精度。要评价 AMB3R 本身，必须改走 se3_native_scale 或 pts + pose 自洽重建（npz 里的 metric_scale 可能是入口，尚未验证）。
projection_report.json 量不了置信度筛掉了多少。 报告里的 claimed_pixels 等于该帧各实例的 point_count 之和， 也就是筛完之后的点数；pixels_without_surface 是写死的 0。 所以想复核"conf 阈值丢了几个像素"，得自己按上面 §02 的流程重算（用 align_mask 取并集、再与 conf ≥ 0.3 比较）。只读报告会得出"几乎没丢"的错误结论。

尺寸有两套，分属两个页面，别混用： assets/frame_XXXXXX.js 自带 width: 518 与 height: 392 （w, h 两个标量）；而已发布的 site/mask_project/meta.js 里，每帧记的是 grid_shape_hw = [392, 518]（h, w）、rgb_shape_hw = [968, 1296] 与 rgb_crop（裁剪偏移，供 2D 底图对齐）。 代码里 AMBR3R_SIZE = (518, 392) 也是 w, h 顺序， 而 npz 的 grid_shape_hw 是 h, w——同一套尺寸在三个地方出现三种写法， 是这块最容易写反的地方。

自己核对一份 source

怀疑某帧投影不对时，不必读源码，pagegen/build_mask_project.py 生成的检查页 就是为此存在的（site/mask_project/）： 

.venv/bin/python -m pagegen.build_mask_project \
  --amb3r-source artifacts/sources/scene0000_00/scene_amb3r_v1 \
  --output site/mask_project --count 20

它对每个 mask 画两侧：左边是该 mask 在 RGB 上的覆盖，右边是它反投影出的三维点。 2D 侧用两种颜色区分声称且投影成功与声称但没有几何的像素—— 后者不产生任何点，在纯点云视图里是隐形的，只有这个页面才看得见。 注意这个页面用的是另一套编码（u16 量化坐标 + 位打包），与 source 里的 assets/*.js 无关，两者各自独立生成、互不读取。

要复核置信度损耗（§02 里报告缺失的那个量），直接算： align_mask 把每个 mask 对齐到 392×518 后取并集，再与 npz['conf'] >= 0.3 比较，差值就是被丢掉的像素。

03harness 框架

src/harness/ · 逐窗口的模型决策循环

输入
02 产出的 source 目录（每帧一堆带归属位的三维点）。
输出
物体身份与归属（版本化状态）、每个物体的累计点云、两套可回放的页面。
命令
python -m src.harness.run；已完成的结果用 --publish-only 只重建页面

到这里，数据是「每帧一堆带归属位的三维点」。还缺的是身份： 第 0 帧的椅子、第 3 帧的椅子、第 7 帧的椅子，是不是同一把。这件事由模型通过工具循环决定。

窗口

帧被切成固定大小的窗口（默认 5）。每个窗口是一笔事务：模型看这一窗， 决定这些观测归给哪些物体，提交，然后进入下一窗。开始时模型拿到的是当前窗口每帧的 RGB 与 overlay、每条观测的类别与几何摘要、全部已归档物体的文字记录与 3D 框。

历史图片一开始不发。 只有文字与几何。要确认某个历史物体长什么样，模型得主动调 inspect_object 或 inspect_observations。

一个窗口的初始输入按 inputs.py 的组装顺序

窗口范围内共 window 帧，每帧恒定 2 张图，所以图片数 = 帧数 × 2， 与物体数量无关。历史越长，增加的是文字档案，不是图片。

一个窗口的生命周期run.py · process_window

窗口是 Harness 里唯一的事务单位。它跑完只有两种结局：提交成功，或 抛错、检查点原样保留。下面是源码顺序，不是示意图。

1
组装输入
inputs.build_window_content → 一条状态 text、逐帧「观测 text + RGB + overlay」、一条历史访问说明。 同时把本窗观测登记进可引用的证据集合，并写 window_inputs/NNNN_context.json 审计。
2
工具循环
最多 max_calls 轮。每轮模型可调任意工具（parallel_tool_calls: false，一次一个）。 工具返回的图片作为下一条 user 消息补进会话，不是塞进 tool 消息里。
3
预算警告
第 max_calls−2 轮之前插入。追加一条 user 文本，要求立刻产出完整提案并提交； 从这一轮起 tool_choice 被强制成 propose_update，模型不能再去看证据。
4
提交与落盘
commit_update 成功才写盘。先写 versions/.NNNN.tmp，算完该版本所有点云再原子改名； 然后写 checkpoint.json = {version, cutoff}。失败不碰旧版本。
5
耗尽即失败
用到 max_calls 轮仍未提交 → 抛 RuntimeError， 整进程停下，检查点仍指向上一个窗口。重跑同一命令从该窗口继续。

网络错误与这个预算分开算：单个请求失败会按指数退避重试 --network-retries 次；若仍失败，--window-network-retries 允许 「保留整段会话、只重发这一条请求」再来几批，每批间隔 30 s。两者都不会消耗轮次。

窗口开始时的空间提示spatial_context.py

  1. 对上一个已提交版本的每个物体，用 versions/NNNN/clouds/*.npz 重新拟合 直立 OBB：RANSAC 找主平面定朝向、平面吸附修正边界、分位数定尺寸、再做低密度尾检查。
  2. 对本窗每条观测，用 KD 树算它的点到每个物体点云的最近距离，取中位数；按这个中位数排序取前 3， 记为 spatial_candidates（至多 15 个，每个有 gap_m 和 overlap）。
  3. 全部结果冻结在窗口开始那一刻（base_version / cutoff）， 窗口内不再刷新——即便模型改了归属。
这一步没有缓存，而且不便宜。 build_spatial_context 直接调 export_version_objects（无缓存版）， 每次窗口开始都把全部历史物体重新拟合一遍。实测：34 个物体约 5.6 s， 51 个约 18.7 s，70 个约 30.9 s（≈ 0.16→0.44 s/物体）。 按 30 个窗口累计，光这一项就是十几分钟——在 2.9 小时的 run 里不算大头，但它是纯本地空转。 页面侧的同类计算有缓存（visualization_cache/bboxes），模型侧刻意不缓存， 以保证模型看到的证据可以由代码与点云完全复现。

五个工具

五个工具按副作用从小到大分三档。取证：inspect_observations / inspect_object 只读，但看过的观测 ID 会登记为可引用证据， 这是提案里 evidence 字段的唯一来源。校验：propose_update 只改内存里的待提交提案，失败不留任何磁盘痕迹。提交：commit_update 是唯一写盘的调用。所有工具都是纯同步调用，没有并行（parallel_tool_calls: false）。

注意"事务"在本页只指一个窗口的完整提交（见上文「窗口是 Harness 里唯一的事务单位」）， 不指某一类工具。早先版本把 propose_update / commit_update 合称"事务工具"， 那与窗口级的含义冲突，且掩盖了两者"一个改内存、一个写磁盘"的区别，已改。

最后一条最容易踩。"所有可见观测"指从第 0 帧到本窗口截止的全部观测， 不是只指本窗新观测。已经处理过的历史观测不必重复列出，但它们必须有状态—— 所以 defer/repair 过的观测也要留在 assignments 里。 实测 150 帧 run 的 213 次调用里有 22 次 propose_update 失败重试， 其中绝大多数就是这一条（漏了某条观测）。

150 帧实跑里的调用分布

指标值

04契约与失效

改哪一段，会让哪一段失效

模块之间不靠命名约定松耦合，而是靠哈希与计数硬校验。上游任何实质改动都会在下游明确失败， 而不是悄悄产生错误结果。

契约位置违反后果
label 文件哈希 predictions.provenance.labels_sha256 改 prompt 或重跑 GPT → SAM 拒绝复用，报"mask 由另一批 label 生成"
RGB 哈希 batch / labels / predictions 三方 + 重算 换图或换帧 → 装配器拒绝
权重一致性 checkpoint 路径 + 大小 + mtime 换 SAM 权重 → 要求换一个新的 --run
每帧 32 mask uint32 位图 超过 → 装配器与 Harness 都报错，不截断
单一模型 装配时汇总 gpt_model 混模型 → 拒绝
lifting_policy harness 框架启动校验 缺省或未知 → 拒绝启动并提示投影命令
asset 四个 base64 键 页面解码 缺一个 → atob(undefined)，整帧白屏
连续采样序号 装配器 非 0 起连续 → 观测 ID 错位，拒绝
取证策略版本 evidence_policy.json（policy version 5） 与当前代码不一致 → 拒绝复用旧目录，要求新 --output
输入文件哈希 input_audit.json（manifest、逐帧 npz、RGB、mask） 任一变化 → Input changed; cannot resume

发布完整性 --publish-only 检查 未跑到最后一帧、或 checkpoint 与 state 不一致 → 拒绝发布

续跑还有一条容易忽略的：检查点 {version, cutoff} 与磁盘上的 versions/NNNN/state.json 是两处独立记录。--publish-only 会显式比对 二者的 cutoff 与 version，不一致直接报 Checkpoint and committed state disagree。

而 input_audit.json 覆盖的是整个 source 的前 N 帧（npz + RGB + 每个 mask）， 不是抽样。实测这 150 帧共 1697 个文件，重算哈希约 0.1 s，150 份 npz 载入约 0.6 s—— 所以准备阶段的成本几乎全在别处（取证图生成），哈希本身可以放心每次全算。

harness 框架的 pending 不是错误。 没被归属的观测会以 defer 收尾，占总数的几个百分点是正常的—— 它代表模型在证据不足时选择不猜，这比强行分配要好。

2026-11-04 起，deferral 不再随窗口广播。原因不是它碍事，而是它没有出路： 一条观测的 mask 只在自己那一窗出现，后续窗口不会重新看到它，所以召回只能靠模型按 id 主动 assign 一条历史观测。在 500 帧全量运行里，这个动作发生了 0 次（8,909 条 assign 全部指向本窗），532 条 deferral 被重新认领的也是 0 条。清单因此只增不减，到末窗 占掉首条消息的 149 KB，而唯一的读者是渲染。现在 defer 仍是合法状态， state.json 仍记录每一条，`listing` 只是不再列它。

05证据边界

这份流水线能证明什么、不能证明什么

前三节描述的是"数据怎么走"。这一节记的是读源码与产物时发现的限制与不成立的说法—— 写报告、做对比、改代码之前先看这里，避免把系统的某个副产品当成另一个东西的证据。

几何

  • 坐标系是对着 GT 拟合的。sim3_oracle_scale 用了 GT 相机位姿， 详见 §02 的 stopnote。它不能用于评价 AMB3R 的独立精度。
  • 只有一份 source 被建立。artifacts/sources/scene0000_00/scene_amb3r_v1， 覆盖 scene0000_00 的 500 帧、4632 个 mask。没有第二个场景， 所以任何"跨场景泛化"的说法目前都没有数据。
  • 页面背景与 lifted 点同一坐标系，背景取自 sim3_ply。装配器虽然也写过一份 assets/background.js（来自 pointcloud_gt_corrected_rgb.ply）， 但投影器会把同名文件整个覆盖，装配器那份不进入最终 source。
  • 跨帧去重对当前 source 不生效。Observations.fused() 有一个按 scene_point_ids 去重的分支，但 amb3r_mask_source 写 npz 时 不写这个键。所以累计点云只靠 2 cm voxel 合并——同一个物理表面在多帧被多次采样时， 是 voxel 把它们压过去的，不是精确的同点去重。

身份与语义

  • 没有准确率评估。summary.json 里 accuracy_evaluated: false， 也没有任何与 GT 实例标签比对的代码。72 个物体是"模型建出来的档案"， 不是"场景里物体的正确清单"。重复建档、漏建档都还没有被量化。
  • 物体级 status 是死的。propose() 建对象时写 status: 'provisional'，之后没有任何代码路径修改它——150 帧 run 的 72 个物体 全部停在 provisional。真正有含义的状态在 assignments 上 （assigned / defer / repair）。 这个字段当前会原样发给模型，读的时候别把它当成"是否置信"的信号。
  • category_label 不是身份。同一物体在不同帧可能拿到不同类别提示， 不同物体也可能同类别。prompt 明确禁止用类别相等来判定同一物体。
  • merge 在实跑里从没被用过。150 帧 run 的 aliases 为空，只有 2 次 relabel。所以"重复建档会不会被合并回去"这件事，目前没有实验证据。

输入侧的已知损耗

  • GPT 承认说不清的区域（unresolved_regions）不会到达 Harness。
  • 27.3% 的提示词一个 mask 都没切出来；67/500 帧触到了 16 个实例的预算上限， 有 414 个候选因此没进 instances。
  • 置信度筛选在个别帧会丢掉最多约 5% 的 mask 像素（帧 75），但 projection_report.json 不记录这个量。

代码里的遗留物

  • src/geometry/incremental_objects.py 的 Associator 是 Harness 之前的手写关联原型，已无生产调用方（只有测试在用）。harness 只从该模块借用 voxelize。
  • src/visualization/publish_gpt_viewer.py 的 main() 是旧 500 帧 发布器的入口，写死了 gpt-5.6-terra 与 500 帧，当前不可用； 但同文件的 rebase_manifest 仍被页面构建调用，所以模块本身不能删。
  • artifacts/sources/scene0000_00/scene_mesh_first_surface_v1 仍在磁盘上， 但其 lifting policy 已不在白名单，Harness 会直接拒绝，代码也无法重建它。
  • run.py 的 --publish-only 分支里有一句重复的 return； README.md 的测试数仍写 199，实际 205。

  --run gpt_sam31_uniform500 \
  --output artifacts/sources/scene0000_00/gpt_sam31_uniform500_v1

.venv/bin/python -u -m src.geometry.amb3r_mask_source \
  --source artifacts/sources/scene0000_00/gpt_sam31_uniform500_v1 \
  --output artifacts/sources/scene0000_00/scene_amb3r_v1 \

# 03 · harness 框架
.venv/bin/python -u -m src.harness.run \

所有重计算都应加 taskset -c 0：本机的 torch 在多核调度下偶发段错误。 这只影响本地计算，与模型调用无关。

harness 参数速查run.py

参数默认影响什么
--output必填实验名（不是路径）。记录写 artifacts/experiments/<name>，页面写 site/experiments/<name>；两者可用 --run-dir/--site-dir 各自覆盖
--sourcescene_amb3r_v1几何来源；lifting_policy 不在白名单直接拒绝启动
--frames / --window30 / 5实验变量：改变模型每窗看到的历史长度。150 帧 run 用的是 150 / 5
--max-calls14每窗 API 轮次上限；至少 4。实测中位只用到 6 轮
--voxel0.02物体累计点云的合并尺度（米）
--timeout120单次网关读超时（秒）；150 帧 run 用的是 600
--model / --reasoning-effortgpt-6-sol / none非 Astra 模型只允许 none；Astra 要求至少 low
--prepare-only—只取证与校验输入，不调模型；改完代码先跑这个
--skip-publish—只存记录，事后用 --publish-only --output <run-dir> 建页
续跑是默认行为，不是选项。目录已存在且 config.json 与 input_audit.json 完全一致时，run 从 checkpoint.json 指向的下一个窗口继续；任何输入或配置变化都会拒绝启动并要求新 --output。 想从头再来就换名字，不要删文件。
