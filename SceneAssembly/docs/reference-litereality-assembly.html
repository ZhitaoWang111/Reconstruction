LiteReality-Agent：组装是怎么做的

它把一次手机扫描变成可仿真的房间。组装分两次：先在物体盒子上把布局修到没有碰撞，再把生成的资产按盒子放进去； 之后由一个 agent 补上小物件并声明支撑关系，最后过一道"几何检查 + 独立看图"的验收。 模型只在几何解决不了的地方出场，而且它的每个提议都要过几何的门。

00总览

五步 · 第 2、3、4 步会调模型 · 每一步后面都有确定性的检查

01
盒子阶段：检查 + 确定性修复
输入 RoomPlan 的墙、门窗、物体盒（中心 / 尺寸 / yaw）  →  输出 违规列表，以及搜索出的最好布局
02
布局 agent：看照片，提一个动作
输入 仍有违规的物体 + 画了盒子的照片  →  输出 通过接受门的修改；过不了门的连同原因回传给下一轮
03
资产进盒
输入 修好的盒子 + 每个物体的 GLB  →  输出 Room.py：资产三个轴分别缩放到盒子的宽、深、高
04
作者 agent：补材质、灯、固定物、小物件
输入 Room.py + 证据包（照片、深度、点云、测量工具）  →  输出 修改后的 Room.py；每个新物体声明 rests_on 或 attached_to
05
验收循环 + 发布
输入 编译出的 Room.glb  →  输出 通过，或交给修复 agent 再来一轮（最多 2 轮）；发布前再做一次网格去穿插和验收
模型
决定"这个盒子哪里错了"：尺寸记深了、该贴哪面墙、是不是两个物体被合并成了一个。还负责补扫描看不到的东西。
几何
算所有厘米数：贴墙距离、角落里裁多少、推开多远、落到台面的高度。并且决定模型的提议留不留。
和我们的差别
它的输入已经有墙体线段和带朝向的物体盒，我们只有扫描点云、地面高度和轴对齐矩阵。它的贴墙类规则我们暂时用不上。

01输入与表示

房间是一段 Python 程序 · 布局是其中一个字典

Room.py
一个确定性的组装器，加一个 SHELL 字典。重新运行它就能重建整个房间，所以任何修改都要落在这个文件里。
SHELL
walls（起点、终点、厚度）· openings（所在墙、偏移、宽高、窗台高）· objects（每件家具一个盒子：center、size、yaw、category）· floor_z、ceiling_z
资产
每个盒子对应一个 GLB。有的是神经网格（TRELLIS），有的是程序化生成、带关节（门、抽屉）。
照片
扫描时的 RGB 帧，带相机位姿和内参；另有 LiDAR 深度和点云。
要点
布局阶段只动 SHELL['objects'] 里的盒子，不碰网格。检查是纯算术，不需要 Blender，也不需要编译出的模型，所以可以在一次修复里试很多次。

02盒子阶段的检查

adjust.py · check() · 修复的优化目标就是它的输出

违规判定阈值
object_clash两个带朝向的盒子在俯视图上重叠，且共享一段高度。穿插深度取最短分离向量的长度共享高度 > 5 cm；重叠 > 1 mm
wall_clash占地越过墙线，或中心落在墙体内越过 > 5 cm
outside_room占地的角点落在地面多边形之外> 5 cm
floating / sunk落地类家具的底面高于或低于地面高 > 8 cm / 低 > 5 cm
below_floor / above_ceiling任何物体穿过地面或天花板> 5 cm
fixture_over_opening 等墙面固定物压在门窗上；门窗不在任何墙上或超出墙的长度—
允许名单
有一张"本来就该重叠"的类别对表：椅子与桌子、水槽与柜子、烤箱与柜子、电视与柜子等。开放式架子（书架、货架）也不参与碰撞检查。检查和修复共用这张表，避免修复器去"修"正确的重叠。
只记不罚
离地但挂在墙上的柜子记为 wall_hung，级别是 info：会写进报告，但不算失败，也不会被修复。

03确定性修复

repair.py · 合法动作搜索 · 不会比输入更差

输入
扫描得到的 SHELL
预处理 · 只动 Z
落地：把悬空的落地类家具放到地面
挂墙的不动；门窗重新对齐到所在的墙
搜索 · 最多 14 轮 · 束宽 3
每个违规提出若干候选动作 → 在副本上执行 → 打分
  • snap：读成"在墙里"的安装类家具，贴回墙面
  • corner_fit：放进两面墙的角落，必要时裁一点
  • slide / dewrap：沿自己靠的墙滑动；同一面墙上的两件沿墙分开
  • separate：按最短分离向量推开，带着同组的物体一起走（桌子带椅子）
  • shrink：盒子记得太深时裁掉一部分，再贴回墙。最多裁 35%
  • push / return：推出墙体；回到地面多边形内
  • drop：删除重复检测。默认关闭，要设 LR_LAYOUT_DROP=1
评分 · 字典序 · 越小越好
（缺陷数，总穿插深度，总位移）
缺陷数 = 违规数 + 被破坏的贴墙关系 + 移动超过 22 cm 的贴墙物体数
输出
搜索过程中见过的最好状态
输入本身也在候选里，所以结果不会比输入差
为什么用束搜索
纯贪心会卡住：有的房间里两件物体必须一起动，任何单步都会让分数变差。束搜索允许中途经过更差的状态，保证只在终点兑现。
为什么穿插排第二
有的修复要两步：先裁掉过深的台面，才露出它和侧墙还有 7 cm 的重叠。如果只数违规个数，第一步就会被丢掉。
为什么默认不删
移错了，看得到一个位置奇怪的盒子；删错了，房间里就少一个烤箱，下游没有任何环节会报告。

04布局 agent

converge.py + agent.py · 确定性修复之后仍有违规才启动 · 最多 6 轮

状态
确定性修复后的布局 + 扫描基线
如果修复结果相对扫描改动过大，整个丢弃，退回扫描原样交给 agent
harness · 选目标
仍有违规的物体（碰撞的两方都算）+ 改动超限的物体
每个目标处理前重新检查一次：前一个修改可能已经顺带解决了它
harness · 给一个物体准备上下文
几何 + 照片 + 之前的失败
  • 这个物体的尺寸、中心、yaw；违规类型、对方是谁、两者共享多少高度
  • 1.2 m 内的墙（到墙面的间隙）；2.5 m 内的邻居，各带 2 张照片
  • 扫描基线里它原来的样子；它被合并前的成员
  • 2 张把当前盒子投影上去的原始帧（按画面占比挑，帧号至少隔 3）
  • previous_attempts：之前被拒的提议和拒绝原因
模型 · 一次调用
读照片，回一个 JSON
resize 给新尺寸 · translate 给新中心 · attach 给一或两面墙的名字 · split 拆回合并前的成员 · none
附 confidence 和一句话理由。用 claude -p，只开放 Read 工具
harness · 执行
先查范围，再在副本上做
单次改动：每个尺寸不超过 60%，中心不超过 0.6 m，高度不超过 5 cm。
attach 的贴墙距离和角落裁剪由几何算；resize 之后自动把物体贴回它原来靠的墙
接受门
（违规数，总穿插深度）严格下降，且没有破坏别的物体的贴墙关系
之后再跑一次确定性修复收尾，并检查相对扫描的累计改动上限
不通过
丢弃，记下原因
原因写进 layout_feedback，下一轮作为 previous_attempts 给模型。
连续两轮没有任何进展就停
通过
成为当前布局
继续处理下一个目标；全部干净就停，状态记为 validated
管线门
从磁盘重新读盒子，再检查一遍
仍有错误就抛异常，管线不往下走。上一份报告里写的"0 个违规"不被信任

相对扫描的累计改动上限

量上限说明
水平位移0.6 m相对保存下来的扫描基线，不是相对上一步。超出的物体算作违规，即使它没有碰撞
垂直位移0.08 m
每个尺寸15%（桌、椅、沙发、床）
35%（其他）
源码原话
"模型选择试什么，几何决定什么是真的。"以及："模型擅长判断'这个衣柜属于那个角落'，不该由它算厘米。"
默认值
代码里布局 agent 默认开启（LR_LAYOUT_AGENT 默认为 1）；同目录的 README 写的是默认关闭，两者不一致，以代码为准。

05实例：过深的台面

根据源码注释整理 · Kitchen 场景的 Oven_Storage_Stove0 · 不是我跑出来的结果

扫描
一段合并后的台面，记录为 2.53 × 1.47 m
厨房台面不会有一米半深。RoomPlan 把相邻的单元合并了，并把深度记长
检查
wall_clash：约半米在后墙里
确定性修复 · 只会平移
失败
往外推，撞上中岛；沿墙滑，还是太深。问题在尺寸，不在位置
模型
看照片后回 resize，给出更浅的深度
第一版实现 · 被门拒绝
绕中心缩小，两个面各缩一半
深度多记了半米，缩小后只从墙里出来四分之一米，违规还在
修正 · 缩完自动贴回墙
模型只给尺寸，位置由几何决定
优先贴违规里点名的那面墙。之前贴的是"先找到的那面"，结果贴到了本来没问题的墙上
结果
通过接受门，写回盒子
修好的盒子同时发给资产生成和房间组装。之前只发给了前者：台面按 63 cm 生成，又被拉回 87 cm 的旧盒子里
这个例子说明
几何对"位置错"有办法，对"尺寸错"没办法，这正是需要看照片的地方。同时，模型给出正确方向之后，落到厘米上的事仍然要几何来做，而且做错了门会拦下来。

06资产进盒

build_room.py · _place_in_box() · 盒子说了算

01
量资产
导入 GLB，取它自己的轴对齐包围盒：宽 aw、深 ad、高 ah、中心
02
量盒子
从盒子取出中心、朝上方向、宽方向、深方向，以及 W、D、H
03
三个轴分别缩放
资产 X → 盒子宽，缩放 W/aw；资产 Y → 盒子深，缩放 D/ad；资产 Z → 盒子高，缩放 H/ah
04
定位
资产中心对齐盒子中心。朝向完全取盒子的 yaw，不按长宽比交换轴
前提
资产必须已经在统一的姿态里：上是 +Z，正面朝固定方向。程序化资产靠生成时的提示词规定这一点。源码注释说：之前按长宽比交换轴，反而把本来对的物体转了 90° 或转反了。
放到台面上
另有 place_on(目标, 资产, 偏移, yaw)：读目标的顶面高度，物体底面落在上面，占地最多缩到台面的一半。
和我们的差别
我们的资产来自 SAM3D，姿态不统一，有的还是倒置的。所以我们多一步"哪面朝上、哪面是正面"的判断；它没有这一步。

07作者 agent 与支撑声明

agent/author.py · 一次自定步调的会话 · 直接编辑 Room.py

这个 agent 负责扫描给不出的东西：墙面和地面材质、灯、插座和暖气这类固定物、桌面上的小物件。它有四套提示词，最新的一套（open）只给目标、证据和验收门，不规定步骤。

证据包

内容用途
全部照片的缩略图总览动手之前先看完，写下房间里有什么
每面墙、地面、天花板的正视拼接图材质和固定物位置的参考
原始帧、位姿、内参、深度、点云测量
probe_depth照片上一个像素对应的三维点
triangulate同一个特征在两张以上照片里点出来，求三维位置。LiDAR 失效的地方用（深色布料、玻璃、细腿）
height_profile给一个占地范围，返回里面有哪些水平面及其高度。用来量桌面、层板的高度
pcd_slice某个高度上的点云俯视切片

每个新增物体必须满足的两件事

成组
一个物体的所有零件用 group_fixture(name, category, parts, ...) 包成一个有名字的整体，比如 Mug0、Radiator0。
声明支撑
rests_on="Table0"、rests_on="Floor0" 或 attached_to="Wall3"，三者必居其一。放在带关节的家具上还要写 support_part，指明是哪个活动部件在托着它。
声明必须是真的
提示词要求：底面的高度从支撑物的顶面读出来，不许凭眼睛摆。"悬空的物体会在仿真第一帧掉下去，穿插的物体会被引擎弹飞。"
为什么不规定步骤
源码注释记录了一次对比：只给原始扫描和一页意图，模型自己先看完所有照片、从深度图量高度、做穿插和接触的自检，结果比照着步骤做的版本更接近照片。规定节奏原本是为了防止模型把预算花在便宜的调用上、最后才动手；作者认为这是 harness 的问题，用结果门解决更好。
权限
open 之前的三套提示词禁止移动家具盒子；open 允许，但要在总结里写明依据的测量值。

08检查与渲染工具

agent 可调用 · 检查只报告不修改 · 渲染永远成对

check_collisions

方面做法
是否接触用编译出的 Room.glb 里的真实三角网格判定（FCL）。只有这样才能分清"椅子塞在桌下"和"椅子穿过桌子"
穿多深、往哪移不取自网格。生成的网格不是水密的，这种网格上的穿插深度不可信（源码举例：贴墙的桌子报出 1.16 m）。深度和方向取自盒子
返回每条结果带解除它所需的移动量（世界坐标 Δx、Δy），以及"移另一个"和"缩小多少"的等价方案
谁决定移动还是缩小由调用方看图决定：只是漂了一点的就移，画得太大的就缩

render

不单独返回渲染图。每张都是同一个扫描相机位姿下的"渲染 | 照片"并排，可以指定整间房、某面墙或某个物体。渲染前如果 Room.py 改过，先强制重新编译，避免 agent 看到旧状态后得出"我的修改没生效"的结论。打分由另一个工具 critic 做，不混进图里。

图片来自仓库的 assets/doc/（Apache-2.0）。

09验收循环

realism_authoring/acceptance.py · 作者 agent 结束后由 harness 执行 · 缺任何一项检查都不算通过

编译
Room.py → Room.glb + room_layout.json
这一轮的房间目录整份留档，不覆盖之前的尝试
检查 1 · 物体没有被改没
物体清单和源网格文件的哈希，与作者 agent 开始前一致
防止通过删掉难处理的物体、或悄悄换资产来过关
检查 2 · 几何
支撑图 + 真实接触 + 网格碰撞
  • 支撑图：每个物体都声明了支撑；目标存在；没有环；沿着链能走到地面、墙或天花板
  • 接触：从物体底面取最多 128 个采样点向下，只和支撑物朝上的三角面求交。间隙和下陷都在 5 mm 内才算接触
  • 稳定性：接触点占比不到一半、且物体中心不在接触点凸包内，判为接触不足
  • 柔性物体（枕头、被子、地毯等）改用整个下表面采样，要求接触面积不小于 1 cm²
  • 挂墙物体：到墙的网格距离不超过 1 cm
  • 碰撞：真实网格的物体互碰、穿墙、挡住门窗。包围盒重叠只列出来供复查，不拦截
检查 3 · 独立看图
另一个模型调用，看 6 组"渲染 | 照片"
它看不到作者 agent 的对话。通过条件：评分 ≥ 8、问题列表为空、声明所有物体都看过。
看完之后再核对一次文件哈希，确保检查的和交付的是同一份
不通过 · 修复 agent
读验收报告，只修报告里的问题
工具只有 render、select_views、check_collisions；默认 40 步、600 秒。
提示词：先修支撑；不许删物体、加看不见的支撑、改检查代码或改报告。
修完回到"编译"。默认最多 2 轮
通过
写 author_acceptance.json
里面有源文件、检查代码和构建产物的哈希。以后只有三者都没变，才认这份通过
三道检查的次序
便宜的在前。物体被改没或几何不过，就不花钱做看图评审。
文档与代码
doc/QC/supporting_relationship.md 说检查只对地面测量，并描述了"支撑物移动时带着上面的物体走"。代码里已经有物体对物体的接触核对；"带着走"的实现我没找到。

10发布

room_qc/publish · 交付前的最后一遍 · 全部确定性，除了最后的验收

01
网格去穿插
对真实网格检测到的物体互碰和穿墙，把能动的那一件推开，只改 SHELL 里的中心。贴墙的安装类家具不动，椅子、桌子、沙发让开；单次最多 30 cm
02
盒子级质量检查
有违规只记为警告，不中止
03
最终编译 + 材质烘焙
失败则中止，候选文件保留
04
对最终产物再做一次验收
和 09 相同的三道检查。不通过则发布失败，状态记为 needs_repair
卡住的四种情况
去穿插收不了尾时区分四种情况：已收敛；需要的移动超过上限（上游摆放有问题）；两件都贴墙、都不能动；轮数用尽。
